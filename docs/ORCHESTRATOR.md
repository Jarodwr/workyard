# Orchestrator event contract

Workyard records state changes but does not send messages to agents itself. A running orchestrator can use `workyard --json events --since <cursor>` to watch the ordered event stream. Store a separate cursor for each Workyard database.

## Task sessions and work selection

After an agent claims a task and moves it to In Progress, attach its runtime session with `session attach`. When the agent waits, use `session pause`, optionally naming the question it is waiting for. This releases an orchestrator worker slot; the task stays In Progress and claimed. The attached session and delivered-event cursor are persisted against the task without changing its content version.

Call `next` when a worker slot opens. Its `dispatch_action` is `resume` for an eligible paused In Progress task or `claim` for a new Backlog task. This is a live query, not a stored queue. Paused tasks take precedence; within each group, current-phase work precedes immediately-next-phase work. A general pause becomes eligible when start blockers clear. A pause for a named question becomes eligible when that question is answered or dropped, even if another blocker remains.

For `resume`, read every `session briefing` page first to capture the current task snapshot and relevant events since `last_delivered_event_id`. Use each returned cursor as `--after` while `has_more` is true; reading pages does not acknowledge them. Then call `session resume` as the atomic dispatch claim. Only the worker whose resume succeeds sends the captured briefing to the runtime. Acknowledge each page cursor only after the runtime accepts that page. If delivery fails, pause the session again for retry; keep unacknowledged pages. A replayed page must be safe to deliver again. The orchestrator owns the actual runtime transport and worker pool; Workyard does not execute or message agents.

## When owned work becomes blocked

Process each returned event in ID order. Inspect its `effects` array. For every effect with `type: "card_became_blocked"` and a non-null `owner_actor`, send that owner a message containing `card_key`, `cause_key`, and the board or card link available in the orchestrator. The message should ask the owner to review the blocker and update its own ticket or status note as appropriate. The orchestrator must not edit the owned card on the owner's behalf.

The effect is emitted only when the card's aggregate derived blocked state changes from false to true. Adding a second blocker to an already blocked card does not create a second blocked notification. The event also contains the primary action and actor that caused the change.

## When a linked question is answered

On each `question_answered` event, read the selected option and explanation from `after`. Its `question_resolved_for_card` effects identify every linked task, including tasks that remain blocked by something else. Check each task's current owner and session before delivery. A paused session receives the answer in its next briefing; a running owner may receive it immediately. Deduplicate by database identity, event ID, and card UUID. The orchestrator must not move or edit the owner's ticket.

For a review question, the owning agent decides whether the answer approves completion or requests changes. It moves an approved ticket to Done itself. If changes were requested, it revises the same ticket and raises another review question when ready. The current schema has no review-specific marker, so the agent/orchestrator must identify review questions by its workflow context. Message delivery is an integration task; the dashboard only records the event.

Example effect:

```json
{
  "type": "card_became_blocked",
  "card_id": "<card-uuid>",
  "card_key": "C-12",
  "owner_actor": "agent:builder",
  "before": { "blocked": false, "ready": true },
  "after": { "blocked": true, "ready": false },
  "cause_key": "Q-3"
}
```

## Cursor and delivery

- Poll with the last processed event ID; follow `has_more` immediately with the returned `cursor`. All events in a page must be inspected, even if none need a message.
- Use `(database identity, event ID, card UUID, effect type)` as a delivery deduplication key. A replay after a restart must not send the same user-visible message twice.
- Persist the global event-consumer cursor and delivery deduplication record in the orchestrator's own storage. The per-task session briefing cursor lives in Workyard's `task_sessions` table and advances only through `session ack` after successful delivery.
- If no orchestrator is running, the board still shows the card as blocked. Do not show a “message sent” state without a delivery acknowledgement from an integrated orchestrator.
- If the owner has released or transferred the card by the time the message is delivered, check the current card before sending and avoid notifying a stale owner.

`owner_actor` is a cooperative local identity string. An attached task session records its runtime and resume ID; the orchestrator still supplies the transport and handles tasks without an attached session.

## Orchestrator host

Status: implemented in the core, the `workyard-orchestrator` crate, and the CLI (`workyard orch ...`), with the Claude Code backend. Codex and terminal-pane backends and delivery of blocked-owner messages to running workers are not built yet. The desktop shows whether an orchestrator holds the board and can pause, resume, or drain it.

- The orchestrator is a long-lived process started with `workyard orch run <board> [--pool N] [--cwd REPO]` and stopped with Ctrl-C, which stops its workers, pauses their sessions, and releases the lease. The `workyard-orchestrator` crate depends only on `workyard-core`'s public commands, never on `rusqlite`, so every action goes through the same validated, evented command layer as the CLI and UI. Its actor is `orch:<board>#<epoch>`, returned by `orch acquire`.
- Runtimes are backends behind a `Runner` trait (`name`, `start`) that returns a `Worker` (`poll`, `stop`). The Claude backend runs `claude -p` on the user's existing login (new: `--session-id <uuid>`, resumed: `--resume <uuid>`), with `WORKYARD_ACTOR`, `WORKYARD_DB`, and a stable copy of this `workyard` binary on the worker's PATH: `orch run` copies its own executable to `<db>.bin/workyard` (replacing it only if different) and puts that directory first, so rebuilding the binary mid-run cannot make worker commands fail with `schema_too_new`. Output goes to `<db>.logs/<card>-<session>.log`. Worker permissions come from `orch run --permissions full|safe` (default `full`, recorded on the board and shown by `orch status` as `permissions`): `full` passes `--dangerously-skip-permissions` (workers run anything; worktrees isolate git state, not the machine), `safe` passes `--permission-mode acceptEdits` and allows `Bash(<cmd>:*)` for workyard, git, node, npm, npx, pnpm, yarn, ls, cat, mkdir, pwd, cargo and python3, plus each `--allow <pattern>`. Repeat `--claude-arg` to replace the permission arguments entirely. Agents report work through board commands (progress, notes, questions, moves), which stay durable events. The worker's exit status supplies only an ephemeral liveness signal.
- Each pass the loop heartbeats, reaps exited workers, and, while the board is `running`, calls dispatch until nothing more should start. A worker that exits with its session paused (waiting) or detached (finished) is normal. One that exits unfinished and unpaused has its session paused so `next` offers it for resume; after `--max-failures` consecutive failures (default 3) the session is detached with a note and the card is **reclaimed**: unowned and back in the backlog (`card_reclaimed`), so the next dispatch starts a fresh worker on it, reusing its branch and worktree. That happens at most twice per card per run; after that a human is notified and the card stays detached. A clean exit (status 0) without finishing counts against that card only. Only a worker that dies with a failure status within 20 seconds counts toward the board-wide fast-failure pause. Resume follows the protocol above: read every briefing page, call `session resume`, start the worker, then acknowledge each page.
- Usage limits are read from structured output, never from message text. The Claude runner uses `--output-format stream-json --verbose` and reads each line as JSON: a `rate_limit_event` whose `rate_limit_info.status` is `rejected` (with `resetsAt` in Unix seconds and `rateLimitType`, for example `five_hour`), or a `result` with `api_error_status` 429, or an assistant message with `error: "rate_limit"`. `allowed` and `allowed_warning` events are not limits. Exit codes are not used: the docs give no code for a limit.
- A limit is not the card's fault. The orchestrator pauses that worker's session without counting a failure and stores a backoff on the board (`orch backoff`, `backoff_until` and `backoff_reason` on `orchestrator_sessions`). While it is in the future, `orch dispatch` returns `dispatch: null` with reason `backing_off`, so nothing starts and nothing resumes. The backoff is the reset time plus a margin (5 s); with no reset time it falls back to 30 minutes, doubling on repeats up to 4 hours. A later time never gets shortened by an earlier report. Afterwards `next` offers the interrupted sessions for resume as usual.
- Three workers in a row (across all cards) that exit unfinished within 20 s of starting also trigger a 10-minute backoff, so a broken setup (auth, permissions, a bad flag) does not walk the backlog failing every card. The reason names the logs.
- **Worktrees.** Each card has a `workspace`: `worktree` (default) or `none` (investigative work). Workyard creates the worktree itself, not the runtime: `<repo>/.workyard/worktrees/<key>` on branch `workyard/<key>` (from the main checkout's current commit, or the existing branch if the card has been here before), kept out of git via `.git/info/exclude`, reused on resume. The worker runs there with no runtime-level isolation, because Claude Code's `--worktree` refuses `git -C <other checkout>` and so stops a worker merging into the main checkout. The prompt names the worktree, branch, main checkout and target branch (the main checkout's current branch), and tells the worker to commit there and record the branch with `link-change`. A `none` card gets no worktree and is told not to modify the repository. Set it with `task add-card --workspace none` or `task workspace <card> <worktree|none>`.
- **Live messages.** Workers run with `--input-format stream-json`. A human note on a card whose worker is running is written to its stdin as a user message, so it is picked up at the worker's next tool boundary (or as its next turn) without restarting it. Notes by the worker itself or by an orchestrator are not forwarded. If a worker cannot take input, the note still reaches it in its briefing when the session next resumes. The process stays alive after a turn until stdin closes, so once a worker has produced a `result` and gone quiet for 1.5 s the engine closes its input and lets it exit.
- **Event pump and notifications.** Each pass the orchestrator reads board events after the cursor stored on the board (a first run starts from now; a restart continues where it left off) and advances the cursor. It notifies a human of a new open question, a commit waiting for review, a card detached after repeated failures, and a backoff, through macOS `osascript` (no dependency; works with the desktop closed). It stops a worker whose card was force-released or transferred. Cancelling needs no stop: only the owner can cancel.
- **Hold.** `session hold` pauses a session and records who has it; `resume_eligible` is false while held, so it is never offered for resume, and the orchestrator stops its worker on the `task_session_held` event. `session release-hold` clears it, and the session resumes through the normal briefing protocol. The desktop's Open in terminal does hold, then opens `claude --resume <session> [--worktree <key>]` in the default terminal, with `WORKYARD_ACTOR` set to the card's owner.
- On start the orchestrator pauses any unpaused session it has no worker for. It stops its own workers on shutdown, so orphans appear only after a hard kill; a worker orphaned that way is not detected.
- At most one orchestrator runs per board. `orchestrator_sessions` holds one row per board: desired state (`running`, `paused`, `draining`), the event cursor, worker pool size, and the lease (holder, pid, `epoch`, `expires_at`). `orch_acquire` takes the lease in an immediate transaction and fails with `orchestrator_conflict` while a live lease exists. A takeover after expiry increments `epoch`.
- Every orchestrator-initiated write carries its epoch in its actor (`orch:<board>#<epoch>`) and is rejected with `stale_epoch` if it is stale, so a suspended or zombie orchestrator cannot act after replacement. The check lives in `record`, which every write calls, so it covers session, ownership, and note commands as well as the orchestrator's own. Lease expiry alone is not the guarantee. A lease is live while unexpired and, for a holder on the same host, while its pid exists.
- `orch heartbeat` renews the lease and returns the desired state, so a running orchestrator learns about pause and drain from it. Heartbeats write no event and publish no tick. `orch cursor` records the last fully processed event and never moves backwards.
- Dispatch is one command, `orch dispatch`: select via the `next` rules, then claim for the worker actor, move to In Progress, and attach the session in one transaction, followed by an `orchestrator_dispatched` event. A paused session is only returned (`dispatch: resume`); the orchestrator reads its briefing and calls `session resume` as described above. Dispatch returns `dispatch: null` with a reason (`paused`, `draining`, `pool_full`, `no_work`) when nothing should start.
- Every committed write writes the latest event ID to `<db>.tick`. `workyard events --follow` and the desktop wait on it instead of polling the database, with a slow fallback poll. The event log stays authoritative, so a missed tick only delays a watcher.
- `orch pause`, `orch resume`, and `orch drain` change the desired state. A paused board dispatches nothing; running workers continue unless draining. Planning edits made while paused are picked up on resume because `next` is a live query.
- On startup the orchestrator reconciles attached sessions with `is_alive`, re-adopting live ones and detaching dead ones.

## Finishing, review, activity (added after the first sample run)

- **Workers integrate themselves.** Finishing means the work is on the target branch: merge the target into the branch and resolve conflicts, run the tests, `git -C <main checkout> merge --ff-only <branch>`, and repeat if the target moved. If the repository documents a merge queue or train the worker follows that, and may `orch session pause <card> --for-integration`. `task move <card> Done` is refused with `not_integrated` until every linked change's branch tip (or recorded commit if the branch is gone) is an ancestor of the repository's target branch (`git merge-base --is-ancestor`); an unreadable repository also blocks. The check runs only on the move, not on reads.
- **`--for-integration`** is a third wait kind beside a question and `--for-review`: `waiting_integration` sessions are offered for resume only when the card's changes are on the target branch, so answering an unrelated question or a human merging later behaves correctly. One wait kind at a time.
- **Review is off unless the board turns it on** (`plan board-review <board> on|off`; `boards.review_required`, shown on board reads). `task link-change` defaults its review gate from the board; `--review-required` / `--no-review` override. The worker prompt mentions `--for-review` only when the board has review on.
- **Activity.** The Claude runner derives what each worker is doing from stream-json (last tool use such as `Edit app.mjs` or `Bash: node --test`, `thinking`, `idle`, plus a tool-use count) and the engine publishes it with `orchestrator_set_activity`: epoch-fenced, no event row, at most every 2 seconds per card, only on change. Board cards' `session` carries `activity`, `activity_at` and `waiting_integration`; the tick file wakes the desktop.
- **Refused tools.** A tool_result error that says a command requires approval, is isolated in the worktree, was blocked, or hit the brace-with-quote check is reported once per distinct text as a notification, and shown as `blocked: ...` activity. Workers are told not to raise a question for such a blocker but to work around it.

## Supervisor agent (optional)

`workyard orch run <board> --supervisor` also starts one long-lived Claude session, the supervisor (actor `agent:supervisor-<board>`, log `SUPERVISOR-*.log`). The script keeps the lease, the pool and every process; the supervisor never starts or stops anything. The script batches what needs judgement (a worker that keeps exiting unfinished, a question raised, a refused tool, a card handed back to the backlog, a backoff) into one message at most every 5 seconds and sends it to the supervisor's stdin. The supervisor acts only through the CLI: it may steer a worker with `task note` (delivered live like a human's note) and answer an engineering question with `admin answer` when the question has a recommended option it agrees with. It must not approve, move, cancel or release cards, edit code or run git; business questions stay with the human. It is restarted up to three times if it exits. It costs tokens only while it handles a message.

`orch run` also loads the Workyard plugin into every worker: `--plugin-dir`, else `WORKYARD_PLUGIN_DIR`, else the app bundle's `Resources/marketplace/plugin`, else `plugin/` above the running binary.
